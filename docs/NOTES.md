# Project notes

Status lives in `docs/PLAN.md` only. Commands and git rules are in `CLAUDE.md`.

## Laptop and protocol facts

- Keyboard firmware is 1.6.
- A 1 ms pause between send and read is needed. Without it, 96 of 100 replies came back broken.
- Fan range is 1600–4500 RPM. Higher speeds are untested.
- Internal screen is 3840×2400 at 60/120/240 Hz.
- An external 4K monitor is attached. Ignore it.
- Touchpad registry value 0 means off.
- `0D85` replies `[2, cpu °C, gpu, 0]` whatever the args. The CPU value is not checked against another sensor.
- The NVIDIA GPU sleeps in D3 when idle. Its power state (`DEVPKEY_Device_PowerData`) can be read without waking it. An NVML read wakes it, and it sleeps again about 1 s later, even with NVML still loaded.
- Mica works in a Slint 1.18 window (stage 22 spike, code in commit 7a330fb). It needs the winit backend with `with_transparent(true)`, `background: transparent` on the Window, then `DwmExtendFrameIntoClientArea(-1)` and `DWMWA_SYSTEMBACKDROP_TYPE = DWMSBT_MAINWINDOW`. Set them after the event loop has run once, since the HWND does not exist before. Without Mica the window is see-through.
- `UISettings` gives the accent colour as RGB 0, 120, 212.
- The accent colour is also in the registry, `Explorer\Accent\AccentColorMenu`, as ABGR (`FFD47800`). The app reads it there, so it needs no WinRT.
- Silent works on the CPU (checked 2026-11-06, CPU on full load, on AC). On Performance the CPU ran at 176% speed and 100 °C, fans 3200 RPM. After Silent it fell to 94% and 60 °C at once. The fans took about 45 s to slow to 1600 RPM.
- Silent and Balanced do not change the CPU and GPU boost values (`0D87`) or the fan target (`0D81`). They stay as Custom left them. The controller seems to use them only in Custom.
- With fans on auto, the fans can stop (0 RPM) at idle in every preset: Silent, Balanced, Performance and Custom (checked 2026-11-06, on AC, CPU load 1–12%, about 2 min each). They start at about 1300–1600 RPM when the CPU gets to about 55–65 °C, and stop again when it cools. Balanced stopped and stayed off below about 54 °C. Performance and Custom switched on and off more often, up to 2000 RPM. The controller has no idle speed between 0 and about 1300 RPM.
- A manual Custom fan never stops: the lowest target is 1600 RPM.
- Windows has its own power mode. On AC it was "Best performance", on battery "Best power efficiency". The app does not change it. A USB capture cannot show if Synapse did.
- The lid logo is LED 4. `0300 [00, 04, on]` sets it, as Synapse does. `0380 [00, 04, 00]` reads back the state just set. `0380 [01, 04, 00]` reads another stored value, which the set does not change (checked 2026-11-06). The `0380` read is not in the capture: it rests on that check and the `cargo hw` logo test. Each switch also sets the effect to static, as Synapse does. The laptop turns the logo on again after a sleep and wake, even when it was set off (seen with the app running, 2026-11-08). So the app saves the switch (`lid_logo` in the config) and sends it at start and after each resume, before the lighting, then reads the state. The read is not on each poll. A set with storage 1, which older models use in open-source code, was not tried as a way to keep the state.
- The charge limit is `0712 [v]`: bit 7 on, low 7 bits the percent. Synapse sends `D0` (on, 80%) or `50` (off), and offers only 80%. `0792 [00]` reads it back with the same layout and the same command id (checked 2026-11-06, it replied `D0`). Synapse then reads `078F` and writes the same flags back with `070F [08]`. The app skips that; the `cargo hw` test checks `078F` stays `08`. The app reads the limit at start and after resume, and reads it back after each set. Whether charging really stops at 80% is not checked yet.
- The touchpad key (numpad ".") is at row 5, column 17 of the key grid (found by eye, 2026-11-07). The app paints it red in the static colour frame while the touchpad is off: at start, after resume, after a lighting change, and each time the touchpad's registry value changes (a `RegNotifyChangeKeyValue` watch, so the physical key counts too). With no saved lighting the app paints nothing. Synapse also sent `0059 [00, 01, x]` on each press, and `00D9 [00, 01, 00]` reads `x` back, but `0059` does not light the key (checked by eye). The app does not send it, since what it does is unknown. `00D9` stays the same when the physical key is pressed. The user saw the key turn red with the window's Touchpad switch off (2026-11-08). The key is "." on the numpad's digit layer (Num Lock on) and the touchpad switch on its second layer, under one light, so it is red only while Num Lock is also off (ticket 72). `GetKeyState(VK_NUMLOCK)` shows Num Lock changes in a process without focus (checked 2026-11-09); the app reads it each 1 s poll.
- The physical touchpad key switches the touchpad in the laptop itself. Windows is not told: its `Enabled` value stays the same, so the red key does not follow that key yet (ticket 47). On a press the keyboard sends input report `04 DD`, then `04 00` on release; Synapse then sent `0059`. Checked 2026-11-07.
- The power-mode key is Fn + numpad Enter. Numpad Enter alone is a plain Enter. The keyboard sends 16-byte input reports on interface 1, usage page 1, usage 0 (two such collections; only one sent them in the probe). Each report is `04`, then the codes of the Razer keys held, then zeros: `0A` is Fn, `D3` the power-mode key, `DD` the touchpad key. Fn + numpad Enter gives `04 0A 00…`, `04 0A D3 00…`, `04 0A 00…`, `04 00…` (read on the laptop 2026-11-07). The keyboard does not change the preset by itself: the `cargo hw` key test reads `0D82` before and after a press. These collections can be read without admin; the keyboard collections can't (access denied).
- Replies and retries in `Device::send` (checked 2026-11-07 and 2026-11-08):
  - Each reply echoes the transaction ID (byte 1) and the command (bytes 6 and 7) of its request, in the Synapse capture and in the `cargo hw` tests that send commands. Bytes 2 and 3 are not compared: some replies set them (`078C` gives `00 02`).
  - A reply that does not match, even a Busy one, is refused and the command is not sent again, since what the controller did is not known.
  - A reply with another transaction ID is read once more after the pause (ticket 51, for the first reply only).
  - The 1 ms pause gave 0 Busy replies or re-reads in 100 reads. With no pause, 94 of 100 failed, most as a short feature report (65 bytes, an Io error), and about a third came back as an older reply. Busy replies in that run echoed the request: the only Busy replies seen on the laptop, and only without the pause.
  - Synapse never sends a request again with its ID (IDs come back only after the 0 to 31 wrap), so each send takes a new ID (ticket 53). A new `Device` starts at a random ID, so a reply left by an earlier run is unlikely to match. `cargo hw` for the controller passed 4 times, each from a random first ID.
  - On Busy the command is not sent again (ticket 55): Busy may mean "taken, still working". The reply is read again 50 ms later (`BUSY_PAUSE`, a guess), up to 5 Busy reads, then `DeviceError::Busy`. No Busy came in the capture, or on the laptop with the 1 ms pause, so the read again after Busy is not checked on the laptop.
  - Other projects on Busy (checked 2026-11-08): OpenRazer treats it as done ("Some commands respond with 'busy' but succeed"), rnd-ash razer-laptop-control and librazermacos ignore it, librazer (razer-ctl) does not check it. Only the JosuGZ fork of razer-laptop-control (3 tries) and r-helper's librazer fork (5 tries, 500 ms apart, on any non-Success reply) resend. None reads again.
- The vapor-chamber light is LED `0x26`. Synapse sets it with each keyboard brightness change, right after the keyboard (`0303 [01, 26, level]`), at the same level. `0303 [01, 26, 00]` turns it off and the keys stay lit (seen on the laptop 2026-11-08). `0383 [01, 26, 00]` reads its level back. Before any change it read 92 while the keyboard read 105, so something other than the app had set it. `0380 [00 or 01, 26, 00]` replies 1 (on); `0382` replies not supported. The app sends level 0 while the switch is off, and the keyboard level while it is on. With the switch off, the light stays off after a brightness change and after a hibernate (checked 2026-11-08). The app sends it again at start and after resume.
- `0D8E` reads back the native mode chosen with `0D0E` at once. The panel stays as it booted.
- Windows Update offers 5 Razer driver updates (read 2026-11-10 with `tools/Block-RazerDriverUpdates.ps1`): Keyboard on `hid\vid_1532&pid_02c7&mi_01&col01`, HIDClass on `usb\vid_1532&pid_02c7&mi_01` (the power-mode key's interface) and on `rzvirtual\...&mi_00&col03`, Razer Device on `razer\devicecontol`, and Mouse on `hid\vid_1532&pid_02c7&mi_02` (the controller's interface). All 10.0.15063.0. Before stage 2 the Mouse one was the `rzdevu_02c7_mou` filter on MI_02. Whether blade-lite still works on these drivers is not known: not tried, since a driver install is hard to undo cleanly. The script hides them (`-Apply`, admin; `-Undo` shows them again). Hiding keeps the other drivers coming. A newer Razer driver would come as a new update, so the app also warns (below). Left from before stage 2: the driver services `RzCommon` and `RzDev_02c7` (stopped) and two `RZVIRTUAL` devices (not present).

## App behaviour

- The window, flyout and popup have window tests (ticket 70, in `cargo t`): Slint's testing backend with its software renderer, over the app tests' fakes (`crates/blade-lite/tests/app/fakes.rs`, also loaded by the binary's tests). `Shell` takes the laptop's parts as a type (`Parts`), so the tests give it fakes and no window test reaches the controller (the test build still compiles the real `Laptop` and `main`). Clicks find controls by role and accessible label, so each control has one. The run's reports go to `target/window-tests/blade-lite-<pid>.log` (quiet). The saved pictures are in `crates/blade-lite/tests/screens/`; GitHub Actions does not compare them, since its fonts differ. The fake controller answers the native mode read with mode 0 whatever was set, so a native mode click shows no restart bar in the tests. Hand checks with `docs/window-check.md` stay for how windows are made and shown, and for what only the laptop shows.
- One copy runs at a time on the PC, by the mutex `Global\blade-lite`. A copy in another user's session should get "access denied" and end (not checked with two users yet). A second start sets the event `Local\blade-lite-open`, and the first copy opens its window. With `--tray` (the autostart start) the second copy ends without that. Checked on the laptop 2026-11-06.
- Autostart is the value "Blade Lite" in `HKCU\...\CurrentVersion\Run`: the quoted exe path, then `--tray`. The tray reads it again on each right click, before the menu opens (in the same call, not posted, so the menu never shows an old tick), and after each click on the item. Only this exe, quoted, then `--tray`, ticks the item; case, spaces and another path to the same file do not matter. A blank value is off. If the value starts another command (such as a copy in `target\debug`), the item says "(set to another program)" and the log names that command once, without control or bidi characters, cut to 200. A click points it at this copy and logs the command it replaced. If the Run key can't be read, the item says "(unknown)" and is not ticked. A `REG_DWORD` value reads as unknown.
- At start and after each resume the app looks for Razer software (ticket 74): running programs (Toolhelp) and running services and drivers (service manager, name and display name) whose name holds "razer" or "synapse", or starts with "rz", in any case. This repo's test programs (`razer_device-*`, `razer_proto-*`) don't count. If one runs, the window shows a warning above the groups while it runs, the log has it when it comes and goes, and the window opens once per run (also from a tray start). A failed look is logged and keeps the warning as it was. If the controller can't be opened at start, the error names the Razer software found. The app still sends its settings while Razer software runs (the ticket asked for no change); the two may then both write. A Razer driver from Windows Update starts a service such as `RzDev_02c7` ("Razer 02c7 Service"), so it is found too; the service name of the MI_02 mouse filter was not read. Stopped services are not counted, so the stopped ones left from before stage 2 give no warning. The THX audio service (`thx_rznb11_*`) has "rz" only inside its name.
- `blade-dev` and the `cargo hw` tests take the one-copy lock. They refuse to touch the controller while the app runs, so quit it first.
- The app steps the presets in the profile order Silent, Balanced, Performance, then wraps. Synapse's order is not known (no capture). Custom is never stepped to, since it may hold a manual fan; from Custom the key goes to Silent. On battery it steps Silent and Balanced only, from the preset that runs, and saves the new one, as a click does. A press within 300 ms of the last step is dropped. The reader opens the reports again after a read error or a minute with no report, so a handle gone stale over a sleep comes back.
- The "Switch to 60 Hz on battery" switch is in the window and the flyout. It flips the saved value, so it works while the controller can't be read. On battery it acts at once. If 60 Hz can't be set, it saves the switch off again, so the rate buttons don't lock at another rate. Both switches are set from the config after each click, even after an error.
- The app writes its errors to `%APPDATA%\blade-lite\blade-lite.log`, as well as stderr. Each line starts with the UTC time. A file moves to `.log.1` at 1 MB; 5 files are kept, so the log never passes 5 MB. A window error is written once, not on each refresh. A panic is written too. If the files can't be moved aside (another program holds one open), the log starts again with a note. A line can hold local paths, such as the user folder. On a full disk a line may be cut. Nothing is sent off the PC. Checked with a release build 2026-11-07.
- A failed read (Windows or controller) is logged as `read failed: <read>: <error>`, then not again for 10 minutes (ticket 50). `DeviceError` text is one plain line with commands in hex; details that change (such as a transaction ID) go in brackets, and the log groups errors by the text before the first bracket (ticket 56).
- A change the laptop took (preset, custom value, lighting, logo) is kept in memory even when the config save fails. The error says `sent, but not saved: ...` and the popup still shows. The next resume and power change send the kept state (ticket 57).
- `Config::save` writes `config.toml.tmp`, syncs it, then renames it over the config. A failed save keeps the old config and removes the temp file (ticket 61).
- A frameless winit 0.30 window keeps `WS_SYSMENU` and the min and max styles, and winit sets its whole style again on each change of its flags (a show, for one). Mica's frame covers the whole window (margins -1), so Windows drew min, max and close over the flyout's header (ticket 58). `platform::hide_caption_buttons` puts a hook (a window subclass) on the flyout that takes those styles out of every new style (`WM_STYLECHANGING`). Ticket 48's inactive windows may be why they showed only after 48; not proven. Checked on the laptop: no buttons.
- The power-mode popup (ticket 48) takes no focus. winit 0.30 `with_active(false)` makes every show of a window inactive, not only the first, so the app sets it for all windows and the window and flyout ask for the focus after each show. If the flyout stops closing on an outside click, or the window does not come to the front, suspect this.

- Slint testing backend (1.18.1, the version must match `slint` exactly): `ElementHandle` finds nothing without debug info in the generated code, so `build.rs` turns it on for debug builds only (`cargo test --release` finds no controls). `set_platform` is per thread, so each test sets its own. With mock time, `mock_single_click` and `mock_drag` work without an event loop. A `Timer` fires only when the test moves the mock time on (`mock_elapsed_time`), which also runs the shell's popup timers.

## Working style

- The user starts one stage or ticket with "next", or asks for a batch run. A batch run stops early if anything needs the user.
- Tickets that need the user (37, 46) are skipped by "next ticket".
- Run a retro about every 5 stages, or sooner if the same thing goes wrong twice.
- The user hibernates the laptop, not sleeps it. A laptop check after a power change (resume, re-apply) must cover hibernate as well as sleep.
- Num Lock after a wake comes from Windows, not the app (the app sends no Num Lock key). The lock screen value `HKU\.DEFAULT\Control Panel\Keyboard\InitialKeyboardIndicators` must be `2`; at the default `0x80000000` the numpad woke as arrows. With `2`, Num Lock keeps its state over a hibernate (on stays on, off stays off). Set to `2` on 2026-11-08 (needs admin).

## Lessons

- Check `docs/PLAN.md` against what is actually built. Stage 5 found the order did not match.
- Threads can share this folder. A merge failed because another worktree held `master`. Check the folder is free before you branch (`stage` skill, step 3).
- In Git Bash, a Windows path written through a heredoc into Python can turn `\b` into a backspace byte. Write such scripts with the Write tool, then check with `grep -c $'\x08' <file>`.
- Slint: typing in a `LineEdit` breaks a one-way `text:` binding. The window resets the field on Enter, on focus loss, and on `changed custom-hex` (ticket 38).
- tray-icon 0.26 calls its handlers on the event-loop thread and opens the menu right after the right-button-up handler returns. A change the menu must show has to run inside that handler, not through `slint::invoke_from_event_loop` (ticket 43).
