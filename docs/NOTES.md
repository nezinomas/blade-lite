## Laptop and protocol facts

- Keyboard firmware is 1.6.
- A 1 ms pause between send and read is needed. Without it, 96 of 100 replies came back broken.
- Fan range is 1600–4500 RPM. Higher speeds are untested.
- Internal screen is 3840×2400 at 60/120/240 Hz.
- An external 4K monitor is attached. Ignore it.
- Touchpad registry value 0 means off.
- `0D85` replies `[2, cpu °C, gpu, 0]` whatever the args. The CPU value is not checked against another sensor.
- The GPU is an RTX 5090 Laptop GPU. `nvidia-smi -q -d TEMPERATURE` (2026-11-10): target and max operating temperature 87 °C; slowdown 2 °C and shutdown 5 °C above that (given as T.Limit offsets), so 89 °C and 92 °C.
- The NVIDIA GPU sleeps in D3 when idle. Its power state (`DEVPKEY_Device_PowerData`) can be read without waking it. An NVML read wakes it, and it sleeps again about 1 s later, even with NVML still loaded. Probe 2026-11-13 (ticket 185, app quit, power state read each second): an NVML start and an NVML close (`nvmlShutdown`, the drop of `Nvml`) each wake it for about 1 s and take about 3 s; NVML left open after one read did not wake it again in 37 s and in 2 runs of 90 s. Windows' adapter temperature (`D3DKMTQueryAdapterInfo`, `KMTQAITYPE_ADAPTERPERFDATA`, the one Task Manager shows) does not wake it, but holds the value from the last wake while it sleeps (38.6 °C for 60 s, then 44.5 °C after a wake for 80 s; once 51.6 °C against NVML's 46 °C), so it is no live reading and the app does not use it. A second read (2026-11-13, the fixed app and Task Manager open, 10 times a second for 5 min): the GPU stayed in D3 with no wake, and the value stayed 46.2 °C (Task Manager showed 46 °C). It moved earlier only because the old app woke the GPU every 8 to 10 s.
- Device power states with the app running (probe 2026-11-13, tickets 186 and 187: `DEVPKEY_Device_PowerData` of 152 devices read 4 times a second for 5 min; a `cargo app` build started 17 min before): no device changed its state. Asleep (D3) the whole time: the NVIDIA GPU and its audio (so that run had likely not read the GPU yet, ticket 185), the mic's device (Intel Smart Sound Technology for Digital Microphones), the Smart Sound bus, the Realtek codec, the Bluetooth radio and the cameras. Awake (D0) the whole time: every HID device (the Razer interfaces, the ELAN touchpad, Intel's HID event filter, a Logitech USB receiver), the Razer USB device and its USB controller. So the app's 1 s mic mute read and its HID device list woke nothing. The probe also made the list itself (41 interfaces, 2 ms, with and without the string requests) and read the display modes (`QueryDisplayConfig`, `EnumDisplaySettingsW`, 169 modes of the one active display): no change either, the GPU stayed asleep. Not checked: the same with the app quit (whether the app holds the Razer USB device awake; the Logitech receiver is on the same USB controller and keeps it awake anyway), a Bluetooth HID device, a USB HID device in selective suspend, an external monitor (none was active).
- Mica works in a Slint 1.18 window (stage 22 spike, code in commit 7a330fb). It needs the winit backend with `with_transparent(true)`, `background: transparent` on the Window, then `DwmExtendFrameIntoClientArea(-1)` and `DWMWA_SYSTEMBACKDROP_TYPE = DWMSBT_MAINWINDOW`. Set them after the event loop has run once, since the HWND does not exist before. Without Mica the window is see-through.
- `UISettings` gives the accent colour as RGB 0, 120, 212.
- The accent colour is also in the registry, `Explorer\Accent\AccentColorMenu`, as ABGR (`FFD47800`). The app reads it there, so it needs no WinRT.
- Silent works on the CPU (checked 2026-11-06, CPU on full load, on AC). On Performance the CPU ran at 176% speed and 100 °C, fans 3200 RPM. After Silent it fell to 94% and 60 °C at once. The fans took about 45 s to slow to 1600 RPM.
- After a game in Performance, then Silent (ticket 37, 2026-11-10, on AC, charge limit on): 66 °C and fans 2300 and 2400 RPM at the click, 53 °C and 1600 and 1700 RPM after 1 min, then 44 to 50 °C and 1500 to 1600 RPM for 12 min (CPU load 1 to 5%). The fans did not stop, though the 2026-11-06 idle check saw them stop at idle in every preset (Balanced below about 54 °C). Silent always sends fans on auto (`Preset::commands`), so the controller picks this speed; the fan byte was not read back. Maybe a warm part the app does not read keeps them on (the GPU read failed). The app's lowest manual fan is 1600 RPM, so it can't make them quieter. Only auto fans were checked: Custom with a manual fan, then Silent, was not.
- Silent and Balanced do not change the CPU and GPU boost values (`0D87`) or the fan target (`0D81`). They stay as Custom left them. The controller seems to use them only in Custom.
- A Custom mode write with the fan byte manual, sent alone (no boosts, no fan targets after it), keeps the `0D81` target as it was, and the fans go to it (ticket 144, `cargo hw` 2026-11-12, firmware 1.6, idle on AC, two runs): the target stayed `0x14` (2000 RPM, set earlier by a full Custom send) and the real speed rose from about 1600 to 2000 to 2200 RPM in 10 s. So a Custom send cut after all its mode writes (a kill, a crash) runs the fans at the target already set. razer-laptop-control's note that a mode write resets the target was not seen. Not checked: the target after a cold boot with no Custom since (laptop check 29), a target set by other software, other firmware, and a cut after only some of the zone writes. The `cargo hw` test refuses to run when the target is outside the model's fan range.

They start at about 1300–1600 RPM when the CPU gets to about 55–65 °C, and stop again when it cools. Balanced stopped and stayed off below about 54 °C. So after a Custom sent while the fans ran on auto (another preset), the fans climb about 100 RPM a second and stall near 2900; the next Custom send, any boosts, lets them go on to the target (less about 100 RPM). The first run fits this too (2900 at 30 s, 3200 after the second send), as does the user's "rpm only grows when I touch slider" (a slider release sends Custom again). Why 2900 is not known. A fourth run (`what_frees_a_manual_fan_stalled_after_a_custom_from_auto`, user's yes): from Performance, Custom CPU 3 / GPU 3 / 3600, then (a) only the two fan targets again after 2 s: a clean climb, 1500 to 3500 at 42 s, held; (b) the whole Custom again after 2 s: 3500, held; (c) the fan targets again after 30 s: 3500, held. Since ticket 173 the app sends the fan targets once more about 2 s after each manual Custom send. The header shows the real speed (`0D88`); the fans settle about 100 RPM under the target, as every probe read.

- The lid logo is LED 4. `0300 [00, 04, on]` sets it, as Synapse does. `0380 [00, 04, 00]` reads back the state just set. `0380 [01, 04, 00]` reads another stored value, which the set does not change (checked 2026-11-06). The `0380` read is not in the capture: it rests on that check and the `cargo hw` logo test. Each switch also sets the effect to static, as Synapse does. The laptop turns the logo on again after a sleep and wake, even when it was set off (seen with the app running, 2026-11-08). So the app saves the switch (`lid_logo` in the config) and sends it at start and after each resume, before the lighting, then reads the state. The read is not on each poll. A set with storage 1, which older models use in open-source code, was not tried as a way to keep the state.
- The charge limit is `0712 [v]`: bit 7 on, low 7 bits the percent. Synapse sends `D0` (on, 80%) or `50` (off), and offers only 80%. `0792 [00]` reads it back with the same layout and the same command id (checked 2026-11-06, it replied `D0`). Synapse then reads `078F` and writes the same flags back with `070F [08]`. The app skips that; the `cargo hw` test checks `078F` stays `08`. The app reads the limit at start and after resume, and reads it back after each set. It sends the limit only when the switch is flipped.
- The controller keeps the charge limit with no app running. The BIOS has its own charge limit setting (the user had set 80% there). It appears to write the same controller value: the app's switch showed on, so `0792` read on at 80%. Whether the BIOS writes its limit back at the next boot, and so undoes the app's off, is not checked. On 2026-11-10, with no Blade Lite or Razer program running, on AC at 79.5% (WMI `RemainingCapacity` 76633 of `FullChargedCapacity` 96363), Windows read `Charging` false, `ChargeRate` 0. After the app's switch was flipped off, it read `Charging` true at about 90 W, and the battery went to 84%. After the switch was flipped on again, it read `Charging` false, `ChargeRate` 0, within about 10 s. So charging stops at the limit, and the app's on and off work with no `070F` send.
- Battery health (ticket 76) is read through the battery class driver: the first `GUID_DEVICE_BATTERY` interface opened read only, `IOCTL_BATTERY_QUERY_TAG` (wait 0), then `IOCTL_BATTERY_QUERY_INFORMATION` at `BatteryInformation`. Not WMI: `root\wmi` `BatteryStaticData` (the design capacity) gave "Generic failure" without admin on 2026-11-10, while `BatteryFullChargedCapacity` (96363) and `BatteryCycleCount` (86) read fine. The IOCTL needs no admin and gave design 97094 mWh, full 96363 mWh, 86 cycles (99%), the same as WMI. A capacity of 0 or unknown, or a full charge over 150% of the design, shows no percent; a cycle count of 0 means the battery counts none.
- The header's "Charging" or "Not charging" (ticket 110) reads `SYSTEM_BATTERY_STATE.Charging` from `CallNtPowerInformation(SystemBatteryState)`, the call the app already makes for the battery rate, not WMI. It is used only when the same read says a battery is present and AC is on. On 2026-11-10, on AC at 84% with the limit on, it read not charging, and WMI `BatteryStatus` read `Charging` false, `ChargeRate` 0 at the same time. A power event clears it until the next poll, so a reading from before the change is not shown. After the charge limit switch, Windows took about 15 s to change the flag (user, 2026-11-10); a charger plug or unplug shows at once, from the power event.
- The touchpad key (numpad ".") is at row 5, column 17 of the key grid (found by eye, 2026-11-07). The app paints it red in the static colour frame while the touchpad is off: at start, after resume, after a lighting change, and each time the touchpad's registry value changes (a `RegNotifyChangeKeyValue` watch, so the physical key counts too). With no saved lighting the app paints nothing. Synapse also sent `0059 [00, 01, x]` on each press, and `00D9 [00, 01, 00]` reads `x` back, but `0059` does not light the key (checked by eye). The app does not send it, since what it does is unknown. `00D9` stays the same when the physical key is pressed. The user saw the key turn red with the window's Touchpad switch off (2026-11-08). The key is "." on the numpad's digit layer (Num Lock on) and the touchpad switch on its second layer, under one light, so it is red only while Num Lock is also off (ticket 72). `GetKeyState(VK_NUMLOCK)` shows Num Lock changes in a process without focus (checked 2026-11-09); the app reads it each 1 s poll.
- The physical touchpad key switches the touchpad, and Windows' `Enabled` value follows it, so the red key does too: with the app running, the physical key turned the touchpad on and the key went back to the lighting colour, and an app started with the touchpad off by that key painted it red (user, 2026-11-10, ticket 47). The 2026-11-07 note that `Enabled` stays the same was wrong, likely read from Claude's shell (below). On a press the keyboard sends input report `04 DD`, then `04 00` on release (read 2026-11-07); Synapse then sent `0059` (Synapse capture, steps 23 and 26). The touchpad is an ELAN device (`ACPI\ELAN0406`, touch pad collection `HID\ELAN0406&COL03`).
- The power-mode key is Fn + numpad Enter. Numpad Enter alone is a plain Enter. The keyboard sends 16-byte input reports on interface 1, usage page 1, usage 0 (two such collections; only one sent them in the probe). Each report is `04`, then the codes of the Razer keys held, then zeros: `0A` is Fn, `D3` the power-mode key, `DD` the touchpad key. Fn + numpad Enter gives `04 0A 00…`, `04 0A D3 00…`, `04 0A 00…`, `04 00…` (read on the laptop 2026-11-07). That is with Num Lock off. With Num Lock on the same keys send only `04 0A`, then `04 00`, and Windows gets a plain Enter (a new line in Notepad). `GetAsyncKeyState(VK_RETURN)` sees it from a process without focus; a quick tap is down about 30 ms. It can't tell the main Enter from numpad Enter, nor an Enter sent by a program; a hook could, and the user ruled hooks out (2026-11-10). Whether Windows also gets an Enter with Num Lock off is not known; the app reads Enter only with Num Lock on (read 2026-11-10). With Num Lock off, numpad Enter alone also steps the preset (user, 2026-11-10; the keyboard's second layer, not the Enter path), and the user is fine with that. The keyboard does not change the preset by itself: the `cargo hw` key test reads `0D82` before and after a press. These collections can be read without admin; the keyboard collections can't (access denied).
- Replies and retries in `Device::send` (checked 2026-11-07 and 2026-11-08):
  - Each reply echoes the transaction ID (byte 1) and the command (bytes 6 and 7) of its request, in the Synapse capture and in the `cargo hw` tests that send commands. Bytes 2 and 3 are not compared: some replies set them (`078C` gives `00 02`).
  - A reply that does not match, even a Busy one, is refused and the command is not sent again, since what the controller did is not known.
  - A reply with another transaction ID is read once more after the pause (ticket 51, for the first reply only).
  - The 1 ms pause gave 0 Busy replies or re-reads in 100 reads. With no pause, 94 of 100 failed, most as a short feature report (65 bytes, an Io error), and about a third came back as an older reply. Busy replies in that run echoed the request: the only Busy replies seen on the laptop, and only without the pause.
  - Synapse never sends a request again with its ID (IDs come back only after the 0 to 31 wrap), so each send takes a new ID (ticket 53). A new `Device` starts at a random ID, so a reply left by an earlier run is unlikely to match. `cargo hw` for the controller passed 4 times, each from a random first ID.
  - On Busy the command is not sent again (ticket 55): Busy may mean "taken, still working". The reply is read again 50 ms later (`BUSY_PAUSE`, a guess), up to 5 Busy reads, then `DeviceError::Busy`. No Busy came in the capture, or on the laptop with the 1 ms pause, so the read again after Busy is not checked on the laptop.
  - Other projects on Busy (checked 2026-11-08): OpenRazer treats it as done ("Some commands respond with 'busy' but succeed"), rnd-ash razer-laptop-control and librazermacos ignore it, librazer (razer-ctl) does not check it. Only the JosuGZ fork of razer-laptop-control (3 tries) and r-helper's librazer fork (5 tries, 500 ms apart, on any non-Success reply) resend. None reads again.
- The mic key is Fn + numpad 0 (mic icon on the second layer). It sends no Razer code: the `04` key reports show only Fn (`blade-dev keys`, 2026-11-11). Windows gets Win + Alt + K (raw input: LWin, Alt, K from the keyboard's interface 0), Windows 11's own "mute in call" shortcut, hence the popup "No supported apps in use for mic mute". `RegisterHotKey` for Win + Alt + K fails with 1409 (the shell owns it). `GetAsyncKeyState` sees LWin, Alt and K down for about 160 ms from a process without focus, and the keys still reach Windows, so the popup stays and an app in a call (Teams) may mute itself too. The app reads them only while Fn is held (as Enter, ticket 59) and then toggles the default capture device's mute (`IAudioEndpointVolume`, eCapture / eConsole; no admin), and paints the key red while that mute is on and Num Lock is off (ticket 73). A mute set elsewhere (Windows Sound) shows too: since ticket 188 the app keeps one endpoint volume and takes Windows' change notices (`IAudioEndpointVolume::RegisterControlChangeNotify`, and `IMMNotificationClient` for a new default mic), and asks `GetMute` only at start, after a new default mic, after Fn + mic, after a wake, after a failed read and once a minute (a dead registration heals); before it, `GetMute` ran each second. The notices come on Windows' threads with no message pump (`cargo hw` mic test, 2026-11-13). A failed read keeps the last state. The keyboard has no telephony HID collection. The light is at row 5, column 16 (checked by eye 2026-11-11).
- Fn + F10 / F11 (keyboard brightness down / up) send no key code of their own: the `04` key reports show only Fn (`04 0A`, then `04 00` when Fn comes up). While Fn is held the laptop steps the keyboard level (LED `0x05`) itself, by 15 (0, 15, 30 ... 225, then 255), and holding the key repeats. `0383 [01, 05, 00]` reads the new level at once. Read on the laptop 2026-11-10 with `blade-dev keys` (prints the key reports and the level for 60 s; quit the app first). The laptop does not move the vapor light (LED `0x26`) on these keys: with the switch off it stayed at 0 while the keyboard stepped (read 2026-11-10), so the app sends it. A step level such as 15 is saved as the nearest percent (6%), so the next start or resume sends `level(6%)` = 16, not 15: a small drift, not a risk. The app reads the level every 250 ms while Fn is held (for at most 30 s of a hold, `BRIGHTNESS_HOLD_LIMIT`; the 5 s `FN_HOLD_LIMIT` of the Enter path froze the slider when Fn stayed held over many F11 presses) and once when Fn comes up, but not during the 2 s pause after a wake (ticket 85). The user wanted the slider to follow live, not only on release (2026-11-10). Any Fn hold reads, so a level that differs from the saved one for another reason (such as after a failed start) is also taken on the next Fn press: the slider then shows what the keyboard really runs. A held read is skipped while the last one still waits on the event loop. Not checked: whether `Instant` counts time asleep on Windows; if not, a release lost just before a sleep could keep held reads going for the rest of the 30 s after the wake pause (reads only take the level the keyboard runs).
- The vapor-chamber light is LED `0x26`. Synapse sets it with each keyboard brightness change, right after the keyboard (`0303 [01, 26, level]`), at the same level. `0303 [01, 26, 00]` turns it off and the keys stay lit (seen on the laptop 2026-11-08). `0383 [01, 26, 00]` reads its level back. The app sends level 0 while the switch is off, and the keyboard level while it is on. With the switch off, the light stays off after a brightness change and after a hibernate (checked 2026-11-08). The app sends it again at start and after resume.
- `0D8E` reads back the native mode chosen with `0D0E` at once. The panel stays as it booted.
- Windows Update offers 5 Razer driver updates (read 2026-11-10 with `tools/Block-RazerDriverUpdates.ps1`): Keyboard on `hid\vid_1532&pid_02c7&mi_01&col01`, HIDClass on `usb\vid_1532&pid_02c7&mi_01` (the power-mode key's interface) and on `rzvirtual\...&mi_00&col03`, Razer Device on `razer\devicecontol`, and Mouse on `hid\vid_1532&pid_02c7&mi_02` (the controller's interface). ## App behaviour

- The window, flyout and popup have window tests (ticket 70, in `cargo t`): Slint's testing backend with its software renderer, over the app tests' fakes (`crates/blade-lite/tests/app/fakes.rs`, also loaded by the binary's tests). `Shell` takes the laptop's parts as a type (`Parts`), so the tests give it fakes and no window test reaches the controller (the test build still compiles the real `Laptop` and `main`). ## Working style

- The user starts one stage or ticket with "next", or asks for a batch run. A batch run stops early if anything needs the user.
- Tickets that need the user are skipped by "next ticket".
- Run a retro about every 5 stages, or sooner if the same thing goes wrong twice.
- The user hibernates the laptop, not sleeps it. A laptop check after a power change (resume, re-apply) must cover hibernate as well as sleep.
- Num Lock after a wake comes from Windows, not the app (the app sends no Num Lock key). The lock screen value `HKU\.DEFAULT\Control Panel\Keyboard\InitialKeyboardIndicators` must be `2`; at the default `0x80000000` the numpad woke as arrows. With `2`, Num Lock keeps its state over a hibernate (on stays on, off stays off). Set to `2` on 2026-11-08 (needs admin).

## Lessons

- The session-end window has its own thread (ticket 159). A sent message such as `WM_ENDSESSION` runs inside any Windows call on the receiving thread that waits on sent messages, such as `ChangeDisplaySettingsExW`; on the app's thread it then came while the app was borrowed, and nothing could be sent (inferred in the ticket 142 review, not seen). Now that thread posts the quit to the Slint loop and waits for it (at most 10 s), serving sent messages while it waits, so a rate put back in the quit that sends to every window does not wait for it. The design rests on Windows waiting for every top-level window of a process, on every thread, before it ends the process: believed, and borne out by laptop check 38 on AC (2026-11-12: the fans slowed at a sign-out, the log had the session-end line); the battery part, with a rate put back, is not checked yet.

- `cargo run` (and so `cargo app`) puts the app in a job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`: when cargo ends, the app is killed at once, with no message and no quit preset. At a sign-out Windows likely ends cargo with its terminal, so laptop check 23 (try 1, 2026-11-12) sent nothing. A second likely cause in that try: a debug build is a console program with no console handler, so the close of its console can end it too. Both are inferred, not seen. Check 23 try 2 through the script passed (2026-11-12): the fans slowed and the log had the session-end line. A process started with `explorer.exe <exe>` from a shell (the script's way) is in a job too, but one that only allows breakaway (flags 0x800). Claude's shell on this laptop runs in a job with no limits (flags 0x0). Read with a small probe (`IsProcessInJob`, `QueryInformationJobObject`), 2026-11-12. A session-end check uses `tools/Start-CheckApp.ps1` (ticket 166). "Start with Windows" must be turned on from a release exe: it saves the running exe's path, and a debug one may miss each session end. On 2026-11-12 the Run key had no Blade Lite value.
- Claude's shell on this laptop read a different `PrecisionTouchPad\Status` `Enabled` than the app, as the same user: 0 the whole time on 2026-11-10, also in a command marked to run outside the sandbox, while the app's switch (which reads that value) showed On and the touchpad worked. Why is not known (perhaps an old or redirected copy of HKCU). Read such state through the app (its window, drawn with `PrintWindow`, which worked even with another window over it, 2026-11-10) or ask the user. Earlier HKCU reads in these notes were not checked again through the app.
- When the user reports a strange laptop state (still fans, wrong mode), ask them to change nothing, and read the state (read only) first. In ticket 86 a mode change came first, so the cause was never proven.
- Check `docs/PLAN.md` against what is actually built. Stage 5 found the order did not match.
- Threads can share this folder. A merge failed because another worktree held `master`. Check the folder is free before you branch (`stage` skill, step 3).
- In Git Bash, a Windows path written through a heredoc into Python can turn `\b` into a backspace byte. Write such scripts with the Write tool, then check with `grep -c $'\x08' <file>`.
- Slint: typing in a `LineEdit` breaks a one-way `text:` binding. The window resets the field on Enter, on focus loss, and on `changed custom-hex` (ticket 38).
- In the Bash tool, `\\` inside a heredoc can reach the script as one `\`, so a scripted edit with backslashes finds nothing. Use the Edit tool for such lines.
- cargo-mutants (ticket 93): `cargo mutants -p razer-proto -p razer-device -j 4 --output target` takes about 5 minutes. On 2026-11-10: 230 mutants, 166 caught, 42 do not build, 22 missed. After the fixes 12 are left. 3 swap a whole hidapi call in `razer-device/src/hid.rs` (`send_report`, `read_report`) for a fixed result; `cargo hw` should fail on them (reasoned from the reply checks, not run with the mutants). 7 were in `HidKeyReports::read`; ticket 96 moved its loop into `KeySources` over a one-method `ReadTimeout` trait, with unit tests over a fake, and a run on `hid.rs` (2026-11-10) caught all the loop mutants. Left there: 6 that swap the thin hidapi calls (`HidKeyReports::read`, `ReadTimeout for HidDevice`) for a fixed result; only a real key press could catch them, and the `cargo hw` key test presses nothing. 2 are harmless: the `colour.rs` touchpad-key bounds `<` to `<=` (a key at row `rows` or column `columns` is never painted anyway). Not in CI (too slow per push); run it again before a release or after a big protocol change.
- Slint 1.18 drops a window `icon` made with `Image::from_rgba8`: the winit adapter sends the icon only when its cache key changes, and a pixel image has none, the same as no image. A window test that reads the property back still passes, so only the laptop shows it. The app gives the icon to winit in the window attributes hook instead (ticket 115). The exe's own icon is a resource that `build.rs` makes with `embed-resource` (`1 ICON "app.ico"`, found in OUT_DIR).
- tray-icon 0.26 calls its handlers on the event-loop thread and opens the menu right after the right-button-up handler returns. A change the menu must show has to run inside that handler, not through `slint::invoke_from_event_loop` (ticket 43).
