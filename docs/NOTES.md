## Laptop and protocol facts

- Keyboard firmware is 1.6.
- A 1 ms pause between send and read is needed. Without it, 96 of 100 replies came back broken.
- Fan range is 1600–4500 RPM. Higher speeds are untested.
- Internal screen is 3840×2400 at 60/120/240 Hz.
- An external 4K monitor is attached. Ignore it.
- Touchpad registry value 0 means off.
- `0D85` replies `[2, cpu °C, gpu, 0]` whatever the args. The CPU value is not checked against another sensor. Probe 2026-11-13 (ticket 193, `the_second_temperature_field_follows_the_gpu`, app quit, idle, read each second for 85 s): the GPU field is 0 while the GPU sleeps. An NVML start woke the GPU and NVML read 43 °C; at the next read (1 s sampling) the field read 43 (`2B`), held it 11 s, then 0. The NVML close woke it again: the field read 44 (`2C`) for 13 s, then 0. So it is the GPU temperature, kept about 10 to 13 s after the GPU sleeps. Only that one point was compared (idle, 43 °C); not checked under load or for its delay while the GPU heats. In the same run, 19 NVML reads on an open handle while the GPU slept each failed (`Unknown`) and the power state, read 1 s after each, never read awake: a read on a sleeping GPU fails, and no wake was seen. A second probe (2026-11-13, `an_nvml_read_does_not_wake_a_sleeping_gpu`, app quit): NVML started (44 °C), the GPU read asleep 0.6 s later, then 60 NVML reads, one a second, each failed (`Unknown`), and the power state, read 10 times a second (600 reads), never read awake. So an NVML read on an open handle wakes a GPU already asleep for no time a 10-a-second read sees. The probes run only with `BLADE_GPU_PROBE=1`. Not checked: a read that lands while the GPU is going to sleep (the race below), and how long a failed read takes.
- The GPU is an RTX 5090 Laptop GPU. `nvidia-smi -q -d TEMPERATURE` (2026-11-10): target and max operating temperature 87 °C; slowdown 2 °C and shutdown 5 °C above that (given as T.Limit offsets), so 89 °C and 92 °C.

An NVML start wakes it, and it sleeps again about 1 s later, even with NVML still loaded. A read on an open NVML handle while it sleeps fails (`Unknown`), with no wake seen at 10 power reads a second (ticket 193, below). Probe 2026-11-13 (ticket 185, app quit, power state read each second): an NVML start and an NVML close (`nvmlShutdown`, the drop of `Nvml`) each wake it for about 1 s and take about 3 s; NVML left open after one read did not wake it again in 37 s and in 2 runs of 90 s. A second read (2026-11-13, the fixed app and Task Manager open, 10 times a second for 5 min): the GPU stayed in D3 with no wake, and the value stayed 46.2 °C (Task Manager showed 46 °C). It moved earlier only because the old app woke the GPU every 8 to 10 s.

- The charge limit is `0712 [v]`: bit 7 on, low 7 bits the percent. Synapse sends `D0` (on, 80%) or `50` (off), and offers only 80%. `0792 [00]` reads it back with the same layout and the same command id (checked 2026-11-06, it replied `D0`). Synapse then reads `078F` and writes the same flags back with `070F [08]`. The app skips that; the `cargo hw` test checks `078F` stays `08`. The app reads the limit at start and after resume, and reads it back after each set. It sends the limit only when the switch is flipped.

It appears to write the same controller value: the app's switch showed on, so `0792` read on at 80%. Whether the BIOS writes its limit back at the next boot, and so undoes the app's off, is not checked. - Battery health (ticket 76) is read through the battery class driver: the first `GUID_DEVICE_BATTERY` interface opened read only, `IOCTL_BATTERY_QUERY_TAG` (wait 0), then `IOCTL_BATTERY_QUERY_INFORMATION` at `BatteryInformation`. Not WMI: `root\wmi` `BatteryStaticData` (the design capacity) gave "Generic failure" without admin on 2026-11-10, while `BatteryFullChargedCapacity` (96363) and `BatteryCycleCount` (86) read fine. - Replies and retries in `Device::send` (checked 2026-11-07 and 2026-11-08):
  - Each reply echoes the transaction ID (byte 1) and the command (bytes 6 and 7) of its request, in the Synapse capture and in the `cargo hw` tests that send commands. Bytes 2 and 3 are not compared: some replies set them (`078C` gives `00 02`).
  - A reply that does not match, even a Busy one, is refused and the command is not sent again, since what the controller did is not known.
  - A reply with another transaction ID is read once more after the pause (ticket 51, for the first reply only).
  - The 1 ms pause gave 0 Busy replies or re-reads in 100 reads. With no pause, 94 of 100 failed, most as a short feature report (65 bytes, an Io error), and about a third came back as an older reply. Busy replies in that run echoed the request: the only Busy replies seen on the laptop, and only without the pause.
  - Synapse never sends a request again with its ID (IDs come back only after the 0 to 31 wrap), so each send takes a new ID (ticket 53). A new `Device` starts at a random ID, so a reply left by an earlier run is unlikely to match. `cargo hw` for the controller passed 4 times, each from a random first ID.
  - On Busy the command is not sent again (ticket 55): Busy may mean "taken, still working". The reply is read again 50 ms later (`BUSY_PAUSE`, a guess), up to 5 Busy reads, then `DeviceError::Busy`. No Busy came in the capture, or on the laptop with the 1 ms pause, so the read again after Busy is not checked on the laptop.
  - Other projects on Busy (checked 2026-11-08): OpenRazer treats it as done ("Some commands respond with 'busy' but succeed"), rnd-ash razer-laptop-control and librazermacos ignore it, librazer (razer-ctl) does not check it. Only the JosuGZ fork of razer-laptop-control (3 tries) and r-helper's librazer fork (5 tries, 500 ms apart, on any non-Success reply) resend. None reads again.

The app reads them only while Fn is held (as Enter, ticket 59) and then toggles the default capture device's mute (`IAudioEndpointVolume`, eCapture / eConsole; no admin), and paints the key red while that mute is on and Num Lock is off (ticket 73). ## Working style

- The user starts one stage or ticket with "next", or asks for a batch run. A batch run stops early if anything needs the user.
- Tickets that need the user are skipped by "next ticket".
- Run a retro about every 5 stages, or sooner if the same thing goes wrong twice.
- Each new probe prints the Razer USB device's power state and its HID interfaces' `SelectiveSuspendEnabled` values first (`print_usb_power_and_suspend` in `crates/razer-device/tests/hardware.rs`), and each note says which sleep it means: Windows sleep (Start menu, Modern Standby), hibernate (lid close), USB sleep (the device's selective suspend), or GPU sleep (D3). The older `cargo hw` tests are not changed (ticket 219).
- The user hibernates the laptop, not sleeps it. A laptop check after a power change (resume, re-apply) must cover hibernate as well as sleep.
- Num Lock after a wake comes from Windows, not the app (the app sends no Num Lock key). The lock screen value `HKU\.DEFAULT\Control Panel\Keyboard\InitialKeyboardIndicators` must be `2`; at the default `0x80000000` the numpad woke as arrows. With `2`, Num Lock keeps its state over a hibernate (on stays on, off stays off). Set to `2` on 2026-11-08 (needs admin).

## Lessons

- A yes/no box that can delete data asks "Delete ...?", so only Yes deletes, with No as the default button, and its answer is logged. The installer's first "Keep your settings?" box (No deletes) led to a false bug hunt in laptop check 67 (2026-11-17): the folder was gone, the user had chosen delete, and with no uninstall log the click could not be read (stage 39). Inno writes each script `MsgBox` and its answer to the log by itself (`Message box (Yes/No): ...` then `User chose No.`, seen in a probe uninstall's log on 2026-11-17). Also: a test that shows boxes on the user's screen is a laptop test, asked first.
- The session-end window has its own thread (ticket 159). A sent message such as `WM_ENDSESSION` runs inside any Windows call on the receiving thread that waits on sent messages, such as `ChangeDisplaySettingsExW`; on the app's thread it then came while the app was borrowed, and nothing could be sent (inferred in the ticket 142 review, not seen). Now that thread posts the quit to the Slint loop and waits for it (at most 10 s), serving sent messages while it waits, so a rate put back in the quit that sends to every window does not wait for it. The design rests on Windows waiting for every top-level window of a process, on every thread, before it ends the process: believed, and borne out by laptop check 38 on AC (2026-11-12: the fans slowed at a sign-out, the log had the session-end line); the battery part, with a rate put back, is not checked yet.

- `cargo run` (and so `cargo app`) puts the app in a job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`: when cargo ends, the app is killed at once, with no message and no quit preset. At a sign-out Windows likely ends cargo with its terminal, so laptop check 23 (try 1, 2026-11-12) sent nothing. A second likely cause in that try: a debug build is a console program with no console handler, so the close of its console can end it too. Both are inferred, not seen. Check 23 try 2 through the script passed (2026-11-12): the fans slowed and the log had the session-end line. A process started with `explorer.exe <exe>` from a shell (the script's way) is in a job too, but one that only allows breakaway (flags 0x800). Claude's shell on this laptop runs in a job with no limits (flags 0x0). Read with a small probe (`IsProcessInJob`, `QueryInformationJobObject`), 2026-11-12. A session-end check uses `tools/Start-CheckApp.ps1` (ticket 166). "Start with Windows" must be turned on from a release exe: it saves the running exe's path, and a debug one may miss each session end. On 2026-11-12 the Run key had no Blade Lite value.
- Touchpad state sources (ticket 239, 2026-11-17, Windows build 26300, read-only probe `tools/Watch-Touchpad.ps1` run in the user's Terminal panel, 250 ms reads): Windows 11 24H2 has `SystemParametersInfoW(SPI_GETTOUCHPADPARAMETERS = 0xAE)` with `TOUCHPAD_PARAMETERS_V1` (11 `UINT`s, version 1 first; `WinUser.h`, SDK 10.0.26100; not in `windows-sys` 0.61). Bit 3 of the 4th `UINT` is `touchpadEnabled`. The touchpad key (twice) and the Settings switch (off, on) each changed the registry `Enabled` and `touchpadEnabled` within the same 250 ms read, and both matched what the user saw (touchpad working, key colour), before a hibernate and after a good wake. `touchpadActive` stayed 1 with the touchpad off, though Microsoft's page says it needs enabled, so it is no use here. `externalMousePresent` was 1 (the Logitech receiver) and `allowActiveWhenMousePresent` 1. The ELAN collection's device status stayed OK throughout. So the wrong key colour of the morning was not seen again; its cause is not known. Since ticket 239 the app logs both sources, Num Lock and its last paint of the key at its first tick and on each change, at most 30 lines an hour (`touchpad: the registry says ..., Windows' touchpad API says ...[, they differ]; Num Lock on|off, the key is painted red|painted plain|not painted`). The first look after a capped hour that differs from the last line is logged.
- Claude's shell on this laptop read a different `PrecisionTouchPad\Status` `Enabled` than the app, as the same user: 0 the whole time on 2026-11-10, also in a command marked to run outside the sandbox, while the app's switch (which reads that value) showed On and the touchpad worked. Why is not known (perhaps an old or redirected copy of HKCU). Read such state through the app (its window, drawn with `PrintWindow`, which worked even with another window over it, 2026-11-10) or ask the user. Earlier HKCU reads in these notes were not checked again through the app.
- When the user reports a strange laptop state (still fans, wrong mode), ask them to change nothing, and read the state (read only) first. In ticket 86 a mode change came first, so the cause was never proven.
- Check `docs/PLAN.md` against what is actually built. Stage 5 found the order did not match.
- Threads can share this folder. A merge failed because another worktree held `master`. Check the folder is free before you branch (`stage` skill, step 3).
- In Git Bash, a Windows path written through a heredoc into Python can turn `\b` into a backspace byte. Write such scripts with the Write tool, then check with `grep -c $'\x08' <file>`.
- Slint: typing in a `LineEdit` breaks a one-way `text:` binding. The window resets the field on Enter, on focus loss, and on `changed custom-hex` (ticket 38).
- In the Bash tool, `\\` inside a heredoc can reach the script as one `\`, so a scripted edit with backslashes finds nothing. Use the Edit tool for such lines. The Edit tool can't match a control byte; there, `perl -pi -e 's/X\x08lade/X\x5cblade/'` works (`\x5c` is the backslash; put back the letter the bad byte ate, ticket 278). Check with `git diff | cat -A`.
- cargo-mutants (ticket 93): `cargo mutants -p razer-proto -p razer-device -j 4 --output target` takes about 5 minutes. On 2026-11-10: 230 mutants, 166 caught, 42 do not build, 22 missed. After the fixes 12 are left. 3 swap a whole hidapi call in `razer-device/src/hid.rs` (`send_report`, `read_report`) for a fixed result; `cargo hw` should fail on them (reasoned from the reply checks, not run with the mutants). 7 were in `HidKeyReports::read`; ticket 96 moved its loop into `KeySources` over a one-method `ReadTimeout` trait, with unit tests over a fake, and a run on `hid.rs` (2026-11-10) caught all the loop mutants. Not in CI (too slow per push); run it again before a release or after a big protocol change.

- The panel in NVIDIA-only mode (ticket 282, read-only reads 2026-11-18 with the user's yes): the NVIDIA driver reports the laptop's panel (BOE NE180QAM-NZ1) as `DISPLAYCONFIG_OUTPUT_TECHNOLOGY_DISPLAYPORT_EXTERNAL` (10), in `QueryDisplayConfig`'s path and in `DISPLAYCONFIG_DEVICE_INFO_GET_TARGET_BASE_TYPE` alike, and `WmiMonitorConnectionParams` gives 10 for its new monitor instance (`DISPLAY\BOE0D54\5&202dd997...`) while the Optimus one (`4&8a73380...`, 0x80000000 internal) stays listed. So the app finds the panel by these ids from the model profile; whether Windows sets `edidIdsValid` for it is checked by laptop check 75. All modes are there in that mode (511, 30 to 240 Hz at 3840 x 2400). No switch to NVIDIA-only mode asked for a restart (user, 2026-11-18).
