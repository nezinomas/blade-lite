# Whole-codebase review (2026-11-17)

A review of all the code on master `d179545`. Read only: no code changed, nothing was run on the laptop, and no app, probe or hardware test was run.
Nothing here is fixed. Tickets 250 to 271 in `docs/PLAN.md` (2026-11-18) cover all 27 findings; finding 26 went into ticket 239.

## How it was done

Three reviewers read the code at the same time, each with Read, Grep and Glob only:

- **Rust**: a senior Rust developer. Threads, error paths, panics, unsafe and FFI, the state machine, the tests. Had `docs/NOTES.md` and `docs/PLAN.md`.
- **Hardware**: a hardware programmer. Every controller send, the sleep, wake, charger and screen-off paths, guards, flash wear, USB and HID. Had `docs/NOTES.md` and `docs/PLAN.md`.
- **Fresh**: no project context. Only the code, `CLAUDE.md`, `CODING_STANDARDS.md` and `docs/protocol-findings.md`. It hunted for rule breaks.

They gave 50 findings (Rust 12, Hardware 16, Fresh 22). Then each finding was checked against the code by a fourth read (the merge pass). Duplicates were joined, and false alarms and things already decided were taken out (see "Taken out"). Last, the `informed-reviewer` checked this report against the code: no cited line was wrong, and its 11 text fixes are in.
Each finding below says who found it, and whether it is **traced** (the code path was read end to end) or a **guess** (it rests on how the controller or Windows behaves, and nothing in `docs/NOTES.md` proves it).

## Short answer

1. In the app, no reviewer found a wrong command byte, a value sent without its range check, or a path that sends Performance or a manual fan on battery or on a known weak charge. Two exceptions are by design: the quit preset's step and `--reset` send Custom with the fans on auto and the lowest boosts on battery (tickets 148, 196). The hardware tests are finding 3.
2. Two findings can leave a manual fan slow under load with no fan guard (1 and 2). Both need the controller to answer badly several times in a row. Up to 2026-11-15 the log had not shown that on this laptop (`docs/design-review-2026-11-15.md`: no Busy line, no reply for another request, no failed preset send). The log was not read again for this review.
3. All three reviewers found the same test gap: one failed read in `cargo hw` can leave Performance running with no app (3).
4. The rest are smaller guards, places where the code does more resends than `CODING_STANDARDS.md` allows in words, flash-wear paths with no cap, and test and tidy items.

## Findings, most risk first

### Hardware risk

**1. After a cut Custom send, the fan guard and the fast heat reads go off, though a manual fan may run.** Found by: Hardware, Fresh. Traced; the trigger is a guess.
- Where: `crates/blade-lite/src/app.rs:480-483` (`manual_fan_runs`), `:731-757` (`set_fan_boost`); `crates/blade-lite/src/app/events.rs:470-495` (`resend_preset`); `crates/blade-lite/src/shell/ticks.rs:374-380` (`heat_interval`).
- What is wrong: `manual_fan_runs()` reads the saved config, not what the controller may run. A click from Balanced to Custom that fails after its mode writes keeps the config on Balanced. The 3 resends then send Balanced. If they fail too, nothing more is sent until a click or a power event. The guard sends nothing, the heat reads drop to each 10 s, and the next window fill shows Balanced with no warning.
- Case: Balanced runs, a manual Custom fan is saved. Click Custom. The 4 mode writes are taken (manual flag), then a boost write gets a wrong reply, Busy or a bad checksum. Such an error keeps the handle (`crates/razer-device/src/reopen.rs:76-84` drops it only on an I/O error, and an I/O error heals itself through the open again and its start). Three Balanced resends fail the same way.
- Then: if the controller took none of the Balanced writes (or only some zones), the laptop still runs Custom with a manual fan at the old target (`docs/NOTES.md`, ticket 144: a manual mode write alone runs the fans at the target already set), with no guard. A wrong reply or Busy can also mean the controller took the Balanced writes; then the laptop runs Balanced.
- Not proven: how likely four such failures in a row are. Merge-pass note: in this state a Quit sends Balanced with no "fans on auto" step first, because `quit_preset` asks for a saved Custom (`events.rs:541-545`); the code's own comment says that a plain mode write ending a manual fan is not checked on the laptop (known since ticket 130).
- Fix idea: while the preset is unsure after a send that carried the manual flag, treat a manual fan as running (guard and 2 s reads on), keep a slow resend, and keep a warning in the window.

**2. A fan guard that is off never turns on while the CPU temperature can't be read.** Found by: Hardware. Traced; the trigger is a guess.
- Where: `crates/ui/src/fan_guard.rs:143` (off: on only by a recent hot reading), `:181-184` (`Track::note` drops a `None` and a value over 125); `crates/razer-proto/src/readings.rs:65-71` (`cpu_from_reply` gives `None` for a first byte not `02` or a CPU byte of 0).
- What is wrong: a guard that is on stays on with no CPU reading (as its comment says). A guard that is off does not turn on. The heat warning gets no reading either. Only a throttled `read failed` log line shows it.
- Case: Custom, fan 1600 RPM, a game. `0D85` answers `[02, 00, ..]` or "reply not understood" for a spell while the GPU read fails too (ticket 156 saw NVML fail). The fans stay at 1600.
- Evidence from the laptop: `0D85` read CPU 0 once on battery, and "reply not understood" came in 3 log lines up to 2026-11-15 (`docs/NOTES.md`, `docs/design-review-2026-11-15.md`). The log says a kind of error at most once per 10 min, so few failures; that each was a single read is not known.
- Not proven: whether the controller speeds a manual fan up by itself (laptop check 19 heard it, not measured).
- Related decision: ticket 163 (user pick) covers GPU reads that fail, not CPU reads.
- Fix idea: with a manual fan running, about 30 s with no CPU reading counts as hot (full speed), logged once.

**3. Hardware tests can leave Performance or Custom running, and do not check the power source.** Found by: Rust, Hardware, Fresh. Traced.
- Where: `crates/razer-device/tests/hardware.rs:228-262` (`each_preset_is_set_and_read_back_and_the_old_one_restored`): `unwrap` in the loop that sets each preset (`:241-243`) and in the put-back loop (`:254`). `:125-143` (`set_and_read`): `unwrap` in the put-back loop (`:138`), so a failed keyboard put-back skips the vapor light.
- Also: the tests that send Performance or a manual Custom (`:228`, `:283`, `:552`, `:780`, `:872`, `:933`, `:992`) do not read the power source or the charger first. Only two tests do (`:1122`, `:1361`).
- Case: `cargo hw`; the read-back after the Performance write fails once. The test panics before the put-back. All 4 zones stay on Performance with no app. On battery this breaks the "never Performance on battery" rule.
- This is the class ticket 160 fixed, for the Custom test only (`CODING_STANDARDS.md`, "Tests").
- Not proven: that a full `cargo hw` run reaches these tests on battery (it depends on the test order and on when the charger test's plug-in comes). A run of one test on battery reaches it for sure.
- Fix idea: keep each `Result`, try every put-back, then assert. One helper that refuses to run unless `platform::on_battery() == Some(false)` and the charger reads full power.

### Missing guards and rule breaks

**4. A failed keyboard put-back after a screen-on is sent again every second, with no cap.** Found by: Hardware, Fresh; noted by Rust. Traced; the trigger is a guess.
- Where: `crates/blade-lite/src/app/events.rs:66-79` (`follow_screen`), `:116-135` (`keys_back_on`); `crates/blade-lite/src/shell/ticks.rs:642-676`.
- What is wrong: a failed put-back leaves `keys_follow` as it was, so each 1 s tick and each click sends `0303 [01, 05, level]` again. An error that keeps the handle (Busy, wrong reply, a short report) means each one may have reached the controller. About 86 000 stored writes a day while it lasts.
- Decided before: ticket 241 chose "a failed put-back is tried again". No cap and no spacing were set. `CODING_STANDARDS.md` names one resend exception (ticket 88, 3 tries).
- Not proven: that the controller ever answers so for long, and that a write with storage byte 1 wears its flash (`docs/NOTES.md`: not known).
- Fix idea: cap and space the tries as `SOURCE_LIGHTING_TRIES` and `SOURCE_LIGHTING_SPACING` do.

**5. Only the mode writes are read back. Boosts and fan targets are trusted on a Success status.** Found by: Hardware, Fresh. Traced.
- Where: `crates/blade-core/src/apply.rs:172-196` (`preset_differs`), `crates/razer-device/src/lib.rs:203-208` (`Device::run` drops each write's reply).
- What is wrong: `0D87` and `0D81` are read only in tests. A fan target the controller did not take shows in the window as taken.
- Not proven: whether a set reply echoes its args.
- Related: ticket 152 (modes only).
- Fix idea: read `0D87` and `0D81` after a Custom send; show and log a difference, never resend for it.

**6. A `WM_CLOSE` to the hidden session-end window ends the watch with no log line.** Found by: Rust. Code path traced; the trigger is a guess.
- Where: `crates/platform/src/session.rs:168-188` (`on_message`), `:156-165` (`Drop`).
- What is wrong: any `WM_CLOSE` goes to `DefWindowProcW`, which destroys the window, and the thread ends. The app runs on. A later sign-out, restart or shutdown then gets no `WM_ENDSESSION`, so no quit preset is sent. `Drop` uses the same `WM_CLOSE`, so the window can't tell its own close from a stranger's.
- Not proven: which programs send `WM_CLOSE` to this window (a `taskkill` without `/F` is one candidate). The installer uses `/F`.
- Fix idea: end the thread from `Drop` with a private message; log and ignore any other `WM_CLOSE`.

**7. `CODING_STANDARDS.md` allows one "send again"; the code has more.** Found by: Fresh; parts by Hardware. Traced.
- The rule: a send that may have reached the controller is not sent again, with one exception (ticket 88: the preset, up to 3 later polls, never in the tick of the failure or the next).
- In the code, each with its reason in a comment, and none in the rule text:
  - A power event sends the preset at once while it is unsure, with no two-tick wait (`events.rs:499-507`; built by ticket 87). Windows tells the power source once at register (`crates/platform/src/power.rs:221`; Microsoft's documentation, not checked on the laptop), and the start runs before the register (`main.rs:638`, `:667`), so a failed start's preset goes again about 1 s later.
  - At the end of an open-again pause, `follow_source()` can send the preset and `start` sends it again in the same call (`ticks.rs:253-258`).
  - While the fan guard is on, the resend count is filled again each time it runs out (`app.rs:735-741`, ticket 129). The condition is "preset unsure", not "the guard's own send failed".
  - The lighting after a charger change, up to 3 tries (`events.rs:355-392`, tickets 244, 246).
  - The sleep's quit preset at a new sleep notice (`ticks.rs:866-898`, ticket 191; the comment says it breaks the rule).
  - The fan targets once more after 2 s (`app.rs:399-408`, ticket 173).
  - The keyboard put-back of finding 4.
- Fix idea: list the accepted ones in `CODING_STANDARDS.md` (the first is ticket 87, the third ticket 129); decide the second, the start-then-notice timing of the first, and the third's condition.

**8. Import, Reset and the Custom sliders send with no charger read first.** Found by: Hardware, Fresh. Traced.
- Where: `crates/blade-lite/src/app/settings.rs:65-70` (`replace_config`), `crates/blade-lite/src/app/clicks.rs:49-51`.
- What is wrong: a preset click and the power-mode key read the charger first (ticket 136). These paths use the power state of the last poll.
- Case: the Razer charger swapped for a USB-C source (no Windows event), then an Import of a Performance config before the next charger poll. With the window open the gap is about 1 s. While Razer software runs there is no charger poll at all (finding 9).
- Fix idea: call `read_charger_at_click()` first on these paths.

**9. While "Razer software" is found, the weak-charger poll and the preset resend are off.** Found by: Fresh. Traced.
- Where: `crates/blade-lite/src/shell/ticks.rs:313-316`, `:278-281`; `crates/blade-core/src/razer_software.rs:35-41` (any running program, service or driver whose name starts with `rz`).
- What is wrong: Performance or Custom keeps running after a swap to a weak USB-C charger, and a failed switch to the battery preset is not sent again.
- Decided before: ticket 145 names the charger follow and the preset resend among what stops, and the user's pick (2026-11-12) kept that. Not spelled out there: that Performance or Custom then stays on a weak USB-C charger.
- Fix idea: keep the charger read and the step down to the battery preset while only non-updater Razer software runs.

**10. A failed charger read on a poll is dropped with no log line.** Found by: Rust, Fresh. Traced.
- Where: `crates/blade-lite/src/app/events.rs:441-442` (`Err(_) => return Ok(false)`). Also silent: `app.rs:567-571` (`read_charge_limit`), `:642-646` (`read_logo`).
- What is wrong: `CODING_STANDARDS.md` asks that every error goes through `report()`. A `078C` read that fails on each poll hides a swap to a weak charger, and the log shows nothing.

**11. The 60 Hz switch can stay on after Windows refused 60 Hz.** Found by: Rust. Traced.
- Where: `crates/blade-lite/src/app/clicks.rs:267-271` (`let _ = self.commit(old);`).
- What is wrong: `commit` changes memory only after a save that works. If the roll-back save fails, memory and file keep the switch on, the rate buttons lock, and the save error is not logged.
- Fix idea: put the old value back in memory whatever the save does, and report the save error.

**12. A bad lighting value in a hand-edited config stops the preset send at start and wake.** Found by: Rust. Traced.
- Where: `crates/blade-core/src/apply.rs:74-76`; used by `App::start` (`events.rs:33-48`).
- What is wrong: `apply` builds the lighting commands before it sends anything, so `brightness = 200` (it loads: the field is a `u8`) refuses the preset too. Nothing is marked unsure, so no resend comes. The error does show in the window.
- Case: the app was killed in Performance, the file is edited by hand, the app starts on battery. Performance stays until a power event or a click.

**13. Each open again ends in a full start, with no limit on how often.** Found by: Hardware; Fresh saw the same path. Traced; the trigger is a guess.
- Where: `crates/razer-device/src/reopen.rs:88-113`, `crates/blade-lite/src/shell/ticks.rs:212-265`, `crates/blade-lite/src/shell.rs:105` (`REOPEN_GAP`, 5 s).

## What the reviewers found sound

- **Protocol and ranges** (all three): report size, checksum, status codes, transaction ID and command echo checked before a reply is used; zone, fan, LED and storage echoes checked in read replies (set replies are not, finding 5); boosts, fan targets (whole hundreds, 1600 to 4500), brightness, charge limit, mode bytes and refresh rate refused when out of range, not clamped. The bytes agree with `docs/NOTES.md`.
- **Custom order**: modes, then boosts, then fan targets; nothing writes a mode after a target but a whole new run.
- **`Device::send`**: sends once; reads again on Busy or a foreign ID, never sends again. `Reopening` never sends twice and holds a new handle.
- **Battery and weak charge**: every preset path in the app goes through `running()`, except the quit preset's fans-on-auto step (Custom, fans on auto, lowest boosts on battery; by design, ticket 196); an unknown source counts as battery; a failed charger read at a click or event counts as weak.
- **Quit, sleep and panic**: `serve` always tries the quit preset, also after an error or a panic (not while a Razer updater holds the controller, ticket 145); fans on auto go first when Custom with a manual fan is the saved preset and Custom runs or the last send failed (not in finding 1's state); the gate closes after it.
- **Threads and borrows** (Rust): each pause gets its decrement of the pause counter; paths that can run while the app is borrowed use `try_borrow_mut`; the GPU thread holds no lock across its read.
- **unsafe and FFI** (Rust): buffers and `OVERLAPPED` outlive each request; handles close once; struct sizes are set; COM init is paired per thread.
- **HID** (Hardware): only paths with VID 1532, PID 02C7 and a USB parent are opened; a short report is refused; a timed-out send or read is never repeated.
- **Config and log** (Rust): the read is capped, the save is temp file then rename, a bad file asks before the defaults; the log rolls at 1 MB.
- **Tools** (Hardware, Fresh): `Set-RazerUsbSuspend.ps1` and `Block-RazerDriverUpdates.ps1` have guards and an undo. No script that was read starts the app as a side effect.
